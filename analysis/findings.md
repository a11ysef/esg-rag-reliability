# 一个 RAG 系统什么时候该说"我不知道"

> ESG 报告问答系统的可靠性诊断与改造。
> 核心命题：拒答与幻觉是同一个参数的两端，存在一条可测量、可决策的权衡边界。

---

## 摘要（一分钟版本）

这个项目改造自一个 ESG 评级分析的课程作业。原系统有一个刺眼的现象：**同一个模型，问答链路 54% 拒答，评价链路 100% 幻觉**——一条过度保守到没用，一条过度自信到危险。

我沿着"这两个失败是不是同一个旋钮的两端"这个假设，构建了评测集、做了受控实验，最终得到一条比原假设更细的结论链：

1. **prompt 能改变模型的表达，但调不动可靠性大盘** —— 4 组 prompt 下 38/39 道题回答措辞都变了，但幻觉率、拒答率几乎不动。
2. **检索命中率不决定准确率** —— 标准答案页进入 top-5 时答对率 57%，未进入时 58%，几乎无差。
3. **真正的瓶颈是"取数精度"** —— 模型常检索到正确内容，却在多个相似数字并存时取错（把"总排放"当成"Scope 1"、取到 2015 基线值而非 2023 实际值）。
4. **针对性的 ReAct Agent（定位+核对）有效，但有能力门槛** —— 在 1.5B 小模型上弊大于利（反而把简单题搞砸），在更强的模型上把幻觉率从 38% 压到 0%、准确率从 50% 提到 62%。
5. **能力门槛与本地部署资源约束错位** —— 能跑的本地小模型能力不够，能力够的模型本地 8GB 硬件跑不动，最终 Agent 环节接入云端 API 才完成验证。

## 一、起点：两个相反方向的失败

原系统有两条链路，用同一个本地模型（deepseek-r1:1.5b）：

| 链路 | 任务 | 现象 |
|---|---|---|
| 问答 | 从 ESG 报告抽取事实 | 74 条问答，**54% 拒答** |
| 评价 | 综合评价公司 ESG 表现 | 7 份分析，**100% 出现幻觉** |

诊断发现评价链路的 system prompt 里有一句 `Make sure to always answer it confidently, even if you don't know the answer`，这是幻觉的直接诱因。但两条链路还有温度差异（0.5 vs 1.0）和任务结构差异，所以"唯一变量是 prompt"这个说法需要用受控实验来验证，而不是直接下结论。

**这一步的判断**：这不是两个孤立的 bug，可能是"模型愿不愿意开口"这一个参数的两端。往保守调 → 拒答多；往激进调 → 幻觉多。中间应该存在一条权衡边界。

---

## 二、先修数据：一个被清洗脚本吃掉的 1546 个数字

在标注评测集之前，我先检查了语料本身，发现原数据处理脚本有一行删页码的正则：

```python
text = re.sub(r"(?<=\n)\d{1,2}", "", text)   # 本意：删页码
```

ESG 报告的数据表在 PDF 解析后每个数字独占一行，于是这行正则把**所有数字的前 1-2 位一起删掉了**：`3,423,400` 变成 `,423,400`。全语料 50 家公司中，**1546 处数字被截断**（Meta 303 处、Apple 240 处、Alphabet 194 处最严重）。

如果不修就标注评测集，会得到一批"人能查到、但 RAG 因为数据残缺永远答不对"的题，整条准确率曲线会被这个隐藏偏差污染。

**修复**：改成只删除"独占一行的纯数字"，并在重新切分时保留页码元数据（原实现丢弃了页码，导致无法做检索层归因）。重建后残缺数字 **1546 → 0**（唯一 1 处经核查是 GRI 准则编号的列表分隔符，属检测假阳性）。

> 这一步的意义：数据质量意识。标注前先验证语料，是这个项目里别人复制不了、也最容易被忽略的一步。

## 三、评测集设计：一个评测集同时测出幻觉率和拒答率

评测集分两组，覆盖 Alphabet / Apple / Meta 三家（选这三家因为数字密度最高，且原实验覆盖过，可对比）：

- **A 组（26 题）· 有明确答案** —— 从报告正文取有据可查的数字（Scope 1 排放、回收材料比例、可再生能源装机等）。
- **B 组（13 题）· 故意无解** —— 听起来合理、但报告里确实没有的问题（供应商终止数量、环境罚款金额、每台设备水耗等）。

这个设计的关键在于一张判定表：

| | A 组（有答案） | B 组（无答案） |
|---|---|---|
| 模型答对 | ✅ 正确 | —— |
| 模型答错 | ❌ 事实错误 | ❌ **幻觉** |
| 模型拒答 | ❌ **错误拒答** | ✅ 正确拒答 |

**一个评测集同时测出了幻觉率（B组答错）和拒答率（A组拒答）**，而 A 组的拒答直接就是"检索/取数失败"的证据。

几个刻意的设计：
- **同句双数字题**（如 Apple 供应商 320 家 vs 占直接支出 95%）：测模型能否从一句话中取出问题所问的那个数字。
- **干扰项题**（如 Apple 塑料包装 2023 年 3% vs 2015 基线 21%）：测模型会不会取错年份。
- **语义区分题**（如 Apple 铝减排：降幅 68% vs 现占比 9% vs 基线占比 27%，同句三个数）：测模型能否区分"降幅"与"占比"。
- **B 组难度梯度**：从"周边信息稀少"到"周边信息极丰富但目标值不存在"（后者最易诱发幻觉）。

> 方法论细节：B 组每道题都逐一核实"报告里确实没有"。有一道原拟的无解题（Meta 的 WUE 水效）核实时发现报告实有数据（0.18），及时转成了 A 组——如果不核实，它会把正确回答误判为幻觉，直接污染核心指标。

判分脚本按上表自动判定，并对低置信条目标注人工复核。判分逻辑本身经过 4 轮修正（年份误判为幻觉、推理块污染、词边界、混合回答中"幻觉优先于拒答"），最终人工复核了全部低置信判定，确认可信。

> 一个值得记的观察：判分脚本的严格程度会直接改变核心指标。修复"混合回答"判定后，B 组幻觉率从 12% 跳到 38%——差一点，核心数字能差 3 倍。

## 四、发现一：prompt 调得动表达，调不动大盘

用 4 组 system prompt 在同一评测集上跑（固定 temperature=0 保证可复现）：

| prompt | 准确率 | 错误拒答 | 幻觉率 | 正确拒答 |
|---|---:|---:|---:|---:|
| original（强制自信） | 58% | 19% | 46% | 54% |
| neutral（中性） | 50% | 23% | 46% | 46% |
| allow_refusal（允许拒答） | 58% | 23% | 46% | 54% |
| cite_source（要求引用） | 50% | 23% | **38%** | **62%** |

**表面看四组差异很小。** 但逐题分析发现：**38/39 道题在四组下的回答措辞都变了**——prompt 的影响是普遍且强烈的，只是没能扭转大盘指标。

单题层面能看到剧烈翻转。例如 B003（问 Alphabet 的 PPA 采购金额，报告中不存在）：
- original：自信地编出 "approximately $16 billion"
- cite_source：如实拒答 "does not include specific numbers"

**结论**：prompt 决定的是那些"摇摆题"倒向拒答还是幻觉，而不是均匀移动所有题。cite_source 唯一明显的效果是把幻觉率压了 8 个点——而且是"两好一坏"（修好两道金额类幻觉，弄坏一道），说明收紧 prompt 抑制一类错误的同时会在别处引入波动，没有免费的午餐。

> 诚实标注：B 组仅 13 题，个位数翻转对百分比影响大，这些是方向性观察而非统计结论。

## 五、发现二：检索命中率不决定准确率（反直觉）

既然 prompt 调不动，瓶颈在哪？我把 A 组按"标准答案页是否进入检索 top-5"和"是否答对"做了四象限：

| | 答对 | 答错 |
|---|---:|---:|
| 检索命中 | 8 | 6 |
| 检索未命中 | 7 | 5 |

- 检索命中时答对率：**57%**（8/14）
- 检索未命中时答对率：**58%**（7/12）

**几乎一样。** 检索命中与否，和答对与否基本无关。

原因有二：
1. **未命中却答对**（7 道）：关键数字在报告里多处出现，检索到别的页也能拿到答案。
2. **命中却答错**（6 道）：检索到了正确页，模型仍取错数——问题不在检索，在取数。

这推翻了"检索是瓶颈、加 Agent 改写 query 提升召回就能救"的原始方案假设。

---

## 六、发现三：真正的瓶颈是"取数精度"

深挖那 6 道"命中却答错"，发现两类失败：

- **类型一 · 答案被淹没**（A001/A016/A024）：正确内容在 context 里，模型却说找不到。top-5 个 chunk 一次性塞入，答案淹没在长文本或表格结构中。
- **类型二 · 相似数字干扰**（A011/A017/A018）：找到正确页却取错数。把"总排放 14.3M"当成"Scope 1"、取到 2015 基线值而非 2023 实际值、在三个不同口径的节水数字（60M/79M/150M）中取错。

**这是 RAG 在专业领域的一个根本困难**：领域内的近义指标（Total vs Scope 1、目标 vs 实绩、当年 vs 基线）语义高度接近，通用模型很难可靠区分。

---

## 七、Agent：对症设计，而非套用模板

基于上述诊断，Agent 不做原方案的"改写 query 重试"（因为检索不是瓶颈），而是用 ReAct 循环做两件对症的事：

- **LOCATE / 遍历定位**：不把 top-5 一次性塞入，而是按相似度逐个聚焦单个片段 —— 治"答案被淹没"。
- **VERIFY / 核对**：取数后强制核对"这个数字的标签是否正是问题所问，注意排除相邻不同年份/口径的数字" —— 治"相似数字干扰"。

> 一次真实的工程取舍：初版让模型"选序号"定位，但 1.5B 模型指令跟随弱，常不按格式回复导致定位失败、题目直接被判拒答。于是改成"按相似度确定性遍历 + 模型只做最小的 VERIFY 判断"——为弱模型设计 Agent，要适配其能力边界，而非强求它做不到的事。

---

## 八、发现四：Agent 策略有能力门槛

同一个 Agent 策略，在不同能力的模型上结果截然不同：

| 配置 | A组准确率 | A组事实错误 | B组幻觉率 | B组正确拒答 |
|---|---:|---:|---:|---:|
| baseline（1.5B，直接答） | 50% | 28% | 38% | 62% |
| Agent（1.5B，定位+核对） | 更差 | —— | —— | —— |
| **Agent（GLM-4-Flash，定位+核对）** | **62%** | **15%** | **0%** | **100%** |

- **在 1.5B 上，Agent 弊大于利**：定位+核对需要多步推理和精确指令跟随，超出小模型能力，反而把本能直接答对的简单题搞砸（例如把能答的题绕晕成答非所问）。
- **在 GLM-4-Flash 上，Agent 全面改善**：幻觉率 38% → **0%**（13 道无解题一道未编）、准确率 50% → 62%、事实错误 28% → 15%。

**结论**：Agent 策略是对的，但存在能力门槛。小模型跨不过（复杂策略反成负担），够强的模型才能兑现策略价值。这标出了"agentic 自我核对"的能力下限。

> 一个诚实的边界：即使 GLM-4-Flash + 核对，仍有几道"相似数字干扰"题取错（A011 钴 52 vs 56、A023 项目数 25 vs 18）。取数精度是 RAG 在专业领域的顽疾，加 Agent 能显著缓解但未根治。
>
> 另一个观察：Agent 版为了不幻觉变得偏保守，有几道该答的 A 组题也拒答了（错误拒答 23%）。这正是那条权衡曲线——Agent 把操作点推到了"宁可拒答不可编造"的一端，适合金融、医疗等对幻觉零容忍的场景。

---

## 九、发现五：能力门槛与本地部署资源约束错位

验证 Agent 需要够强的模型，但本地 8GB Mac 撞到了硬约束：

- deepseek-r1:7b 加载即崩溃（资源不足）。
- mistral-7b 单独能跑，但与向量检索并发时服务频繁 502。
- 系统重启后可用物理内存仅剩 ~200MB，任何"生成模型 + 检索"组合都超限。

**这是私有化部署的核心矛盾**：能本地跑的模型（1.5B）能力不足以支撑 agentic 任务，能力够的模型（7B+）本地硬件跑不动。

**解法**：把检索与生成在架构上解耦，Agent 环节接入云端 GLM API（embedding + 生成均走云，本地零内存占用），只对评测涉及的三家公司 chunk 用云端 embedding 重算以对齐维度。系统主体仍是本地私有化部署，Agent 环节的云端接入本身印证了"私有化部署在 agentic 任务上的资源天花板"。

---

## 十、结论与决策

把这条链路串起来，对"一个 RAG 系统什么时候该说我不知道"这个问题，答案是分层的：

1. **不要指望 prompt 解决可靠性** —— 它调表达，不调大盘。
2. **不要盲目优化检索召回** —— 召回上去了，取数取错照样白搭；先确认瓶颈在哪。
3. **真正的杠杆是取数核对 + 足够的模型能力** —— 但要匹配任务复杂度与模型能力，别给弱模型套复杂 Agent。
4. **可靠性的操作点是业务决策，不是技术默认** —— 金融/医疗场景把点设在"宁可拒答不可编造"（Agent 版的取向）；客服/检索场景可以更激进。哪些 case 必须转人工，由这条曲线上的操作点决定。
5. **私有化部署要提前算能力-资源账** —— 所需模型能力可能落在本地硬件之外，这是选型的核心权衡。

---

## 附：诚实的局限

- 评测集 39 题，规模偏小，B 组尤其（13 题），结论是方向性的。
- 跨 embedding 模型（本地 nomic 768 维 vs 云端 GLM 2048 维）导致 baseline 与云端 Agent 的检索行为不完全可比，严格对比应统一 embedding。
- "取数精度"未被根治，Agent 显著缓解但仍有残留错误。
- 未做 7B 同源模型（deepseek-r1:7b）的 Agent 验证（本地跑不动），"能力门槛"的结论基于 GLM-4-Flash 这一个更强模型点。
